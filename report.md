# DWH продаж и маркетинговых кампаний

## Запуск

Запустите SQL внутри контейнера Greenplum 7. Для образа из задания, после копирования файлов в `/tmp/sales_project`:

```bash
source /usr/local/gpdb/greenplum_path.sh
psql -X -U gpadmin -d postgres \
  -f /tmp/sales_project/01_setup.sql \
  -f /tmp/sales_project/02_sales_performance.sql \
  -f /tmp/sales_project/03_reports.sql
```

Первый скрипт создаёт учебную базу `sales_marketing` и загружает STG и DDS. Второй пересобирает витрину. Третий выполняет четыре бизнес-запроса и выводит планы. Повторный запуск обновляет весь синтетический набор с новыми случайными значениями. Скрипты рассчитаны на отдельную учебную базу.

## Модель и загрузка

В STG пять таблиц. Данные за январь–март 2025 года генерируются через `INSERT`, `generate_series`, `random()` и `CASE`. Четыре позиции формируют сумму каждого заказа. Статусы представлены 1 080 завершёнными, 60 отменёнными и 60 возвращёнными заказами. В DDS клиенты, каналы и кампании представлены измерениями с бизнес-ключами. Факты хранят заказы и позиции в исходном зерне. Во всех пяти таблицах DDS есть `load_dt` и `load_src`. Ссылки проверены соединениями после загрузки.

| Слой | Наполнение |
| --- | --- |
| STG | 120 клиентов, 4 канала, 10 кампаний, 1 200 заказов, 4 800 позиций |
| DDS | Те же объёмы в трёх измерениях и двух фактах |
| CDM | 900 строк, одна на день и кампанию |

## Метрики

`orders_count`, `customers_count`, `order_amount` и `avg_order_amount` рассчитываются по завершённым заказам. Клиент считается новым в день первой завершённой покупки и относится к её кампании. При одинаковой дате выбирается меньший ID заказа. Сумма `new_customers` по витрине равна числу уникальных покупателей с завершёнными заказами. Дневное количество уникальных клиентов нельзя складывать для оценки уникальных клиентов за месяц.

`revenue` равен сумме завершённых заказов. Поскольку отдельного источника затрат нет, `spend` моделируется как 90%, 100%, 110% или 120% бюджета в зависимости от канала. Сумма распределяется по календарным дням кампании с компенсацией округления. `campaign_budget` хранит полный бюджет, поэтому в отчёте по затратам он берётся один раз на кампанию. ROI равен `(revenue - spend) / spend`. Для периода ROI пересчитывается по суммам выручки и затрат. При нулевых затратах ROI не определён.

## Распределение и оптимизация

Заказы и позиции распределены по `order_id`. В тесте факты заказов разложились по 600 строк на каждый из двух сегментов. Маленькие измерения DDS реплицируются для локальных соединений. Заказы STG и DDS разбиты на месячные диапазоны по `order_dt`. Позиции остаются в одной таблице, поскольку дата находится в заказе. После загрузки выполняется `ANALYZE`.

План без ограничения даты сканировал три партиции заказов. Февральский диапазон оставил одну, а оптимизатор применил индекс первичного ключа. В обоих планах соединение заказов и позиций выполнялось без `Redistribute Motion`. `Gather Motion` собирал частичные суммы. Сканирование позиций оставалось полным, поскольку фильтр задан по дате заказа.

Витрина распределена по `campaign_id`, что позволяет агрегировать кампанию на одном сегменте. Февральский запрос читал готовые дневные агрегаты через индекс без соединения фактов. Десять ключей дали перекос 720/180 строк на сегмент. Пробное распределение по паре `(campaign_id, report_dt)` дало 431/469 строк, но потребовало `Redistribute Motion` для итогов по кампании. Для маленькой витрины оставлено распределение по кампании. При росте объёма этот компромисс стоит пересмотреть на реальных планах и нагрузке.

## Проверка

Развёртывание выполнено с чистого состояния в Greenplum 7. Контрольные запросы подтвердили объёмы, ссылки, суммы позиций и дневные агрегаты. В CDM вошли все 1 080 завершённых заказов и 120 первых покупок. Формулы затрат и ROI совпали с независимой сверкой. Штатная автопроверка курса не запускалась. В полученном задании нет команды или файла для её запуска.
